# release-note — git 히스토리를 사용자 관점 릴리즈 노트로

> **한 줄 요약** — 두 릴리즈 사이의 git 커밋을 수집해, 커밋을 1:1로 나열하는 대신 사용자 관점 테마로 묶은 한국어 릴리즈 노트 문서를 산출합니다.

## 무엇을 만들어 내는가

프로젝트의 기존 릴리즈 노트 관례를 따르는 마크다운 문서 한 개
(`docs/release-notes/` 또는 `CHANGELOG*`). 관례가 없으면
`references/template.md` 의 기본 템플릿을 씁니다.

**핵심 원칙**: 커밋은 *무엇이* 바뀌었는지 말해주고, 릴리즈 노트는 그것이
*사용자에게 어떤 의미인지* 말해줍니다.

## 언제 쓰는가

버전을 하나 끊어 내보낼 때. 이전 릴리즈 경계(태그 또는 직전 릴리즈 노트의 커밋)
부터 현재까지의 변경을 사용자에게 설명해야 할 때.

## 언제 쓰지 않는가 — 형제 스킬과의 경계

이 스킬의 입력은 **git 히스토리** 입니다. 대화 내용이 입력인 나머지 넷과 여기서
갈립니다.

| 입력 | 스킬 |
|------|------|
| git 히스토리 (커밋 범위) | **`release-note`** (이 스킬) |
| 현재 대화 — 사건 하나 | `notes:rca`, `notes:blog-dev-learnings` |
| 현재 대화 — 패턴 하나 | `notes:insight` |
| 현재 대화 — 오늘 한 일 | `notes:task-history` |

한 세션에서 한 작업을 요약하는 것은 `task-history` 이지, 릴리즈 노트가 아닙니다.

## 호출 형식

```
/notes:release-note [<anchor-ref>] [<head-ref>]
/notes:release-note -h | --help | help
```

인자를 주지 않으면 앵커를 스스로 찾습니다. `-h` / `--help` / `help` 는
`references/help.md` 를 그대로 출력하고 종료합니다.

## 동작 단계

단계 1~5 는 순차입니다. 앵커를 찾을 수 없거나 저장 경로 쓰기에 실패하면 즉시
보고하고 다음 단계로 가지 않습니다.

1. **앵커 커밋 찾기** — 우선순위: (1) git 태그, (2) 이전 릴리즈 노트 문서에 적힌 커밋, (3) 사용자에게 시작점 확인. 명령은 `references/git-commands.md` 참고.
2. **커밋 수집 및 분류** — `<anchor>..HEAD` 범위를 conventional commit prefix 별로 분류: `feat`, `fix`, `refactor`, `docs`, `chore`, 그리고 **비관례 커밋**.
3. **테마로 그룹핑** — 가장 중요한 단계. 같은 컴포넌트의 여러 `feat:` 는 하나의 테마로, `feat:` + 관련 `fix:` + `refactor:` 는 기능 개발 전체를 묶는 섹션으로. 규칙은 `references/grouping-heuristics.md`.
4. **작성** — 프로젝트의 기존 릴리즈 노트 포맷이 최우선. 없으면 기본 템플릿.
5. **저장 및 커밋** — 파일을 쓰고 `docs: add <version> release notes` 로 커밋한 뒤 한 줄 verdict 로 보고.

## 주의사항과 제약

- **비관례 커밋을 반드시 확인하세요.** `grep -vE` 로 걸러지는 커밋이 가장 놓치기 쉽습니다 — 스킬이 이 단계를 명시적 경고로 표시합니다.
- **커밋을 1:1로 나열하지 마세요.** 이것이 이 스킬이 존재하는 이유입니다. 테마 이름에 구현 용어를 쓰지 않습니다.
- **프로젝트 관례가 템플릿보다 우선** 합니다. 기존 릴리즈 노트가 있으면 그 포맷을 따릅니다.
- 태그가 없는 프로젝트에서는 앵커 판정이 직전 릴리즈 노트에 적힌 커밋으로 넘어가고, 그것도 없으면 사용자에게 묻습니다. 커밋이 하나뿐인 신규 repo 에서는 앵커가 없어 진행하지 못합니다.
- 흔한 실수 체크리스트는 `references/grouping-heuristics.md` 의 "흔한 실수" 절에 있습니다.
